# CMC

An **unofficial**, read-only companion app for the
[Colégio Marista de Carcavelos](https://marista-carcavelos.globaleduca.com/) website.

Not affiliated with, endorsed by, or connected to the Colégio in any way. All content
belongs to the school and is read from its public website. The app never writes
anything back.

Four features:

| Tab | What it does | Source |
|---|---|---|
| **Destaques** | The homepage highlights, natively. Tap opens the PDF/page in-app. | `/` |
| **Calendário** | The school year, with "Próximos", search, add-to-calendar and `.ics` export. | `/calendario-geral/` |
| **Ementas** | The monthly canteen menus. | `/oferecemos/refeitorio-ementas/` |
| **Notificações** | A local notification when a new Destaque is published. | `ultima_hora` REST API |

**Read [`PLAN.md`](PLAN.md) before changing anything substantive.** It is the design
record: the verified structure of every page, the exact selectors, and the parsing
hazards. Do not re-derive that research.

## Running it

Open `CMC.xcodeproj` and run. Requires Xcode 26+.

- **iOS 17+** is the real target and the one the UI is designed for (the HIG is rule 1).
- **macOS 14+** also builds and runs, so the project can be built and tested without an
  iOS simulator installed. Every platform difference lives in `Views/Common/Platform.swift`
  and in the three sheet files (`WebSheet`, `QuickLookSheet`, `EventEditSheet`) — the
  screens themselves contain no `#if os(...)`.

One dependency: [SwiftSoup](https://github.com/scinfu/SwiftSoup) (SPM, resolved
automatically). This app is fundamentally an HTML scraper against markup we do not
control; regex-parsing HTML is the classic unmaintainable trap. See PLAN §3.2.

### Tests

```
xcodebuild test -project CMC.xcodeproj -scheme CMC -destination 'platform=macOS'
```

45 tests, all offline. They parse checked-in copies of the three real pages from
`CMCTests/Fixtures/`, so they are deterministic and fast, and they assert the exact
invariants from PLAN §2 — 12 calendar months, 104 events, both ementas tracks, every
Destaque with a non-nil URL.

## The site changed, now what?

This is the single most likely maintenance task. The website is out of our control and
its markup is generated by Elementor, so class names change without notice.

1. **Refresh the fixtures:**

   ```
   Scripts/refresh-fixtures.sh
   git diff --stat CMCTests/Fixtures
   ```

2. **Run the tests.** The failing test names what broke — e.g. *"Exactly 104 events —
   the accordion is not read twice"* means the calendar accordion changed shape.

3. **Fix [`CMC/Services/Selectors.swift`](CMC/Services/Selectors.swift).** Every CSS
   selector and regex in the app lives in that one file, each with a comment recording
   what it matched and when. You should not need to touch a parser.

4. **Update PLAN.md §2** with what you found and re-date it. That section's value
   depends entirely on being trustworthy.

Meanwhile, users are fine: every screen caches its last good result and shows it with a
visible "última atualização", so a broken site degrades to stale data, never an empty
screen. Parse warnings appear in a collapsible footnote at the bottom of each screen —
that is the early-warning signal.

## How the code is laid out

Deliberately flat. No architecture ceremony (rule 2). No file over 200 lines.

```
CMC/
  CMCApp.swift              app entry, background-task registration, notification routing
  Models/                   plain Codable data
  Services/
    Selectors.swift         ★ every CSS selector and regex, in ONE file
    SiteClient.swift        ★ the only place URLs are built and URLSession is called
    *Parser.swift           pure functions: String (HTML) -> ([Model], [Warning])
    *Store.swift            one per screen: fetch, cache, expose
    Cache.swift, ICSExport.swift, NotificationService.swift, BackgroundRefresh.swift
  Views/                    one file per screen, plus DestaqueOpener (the only PDF viewer)
CMCTests/
  Fixtures/                 saved copies of the three real pages
```

To add a screen, copy an existing `Store` + `View` pair.

### Two rules worth repeating

- **Parsers never throw on partial failure.** They return what they understood plus a
  list of warnings. One malformed calendar entry must not blank a screen.
- **Never fabricate.** Ementas filenames look predictable — they are not, and one is
  misspelled. If a menu is not listed, the app says *"Sem ementas publicadas"*. A date
  we cannot read (`8 ou 22 de maio`) is shown verbatim and is not exportable, rather
  than silently resolved.

## Known platform limit

iOS **cannot** guarantee a daily morning fetch for an app with no server.
`BGAppRefreshTask` takes an *earliest* begin date; iOS decides when, or whether, to run
it. The app therefore also runs the same diff on every foreground, which is what makes
the feature dependable in practice — a background miss costs latency, never a lost
notification. See PLAN §6.1.
